# Gate G3: search (task P2-4)

Gate G3 compares the search of the Rust server with the search of the Python
server v5.19.0 on the same records. The keyword side is the Qdrant sparse
vector of decision P0-2 (`docs/decisions/2026-11-16-rust-keyword-index.md`).
The tantivy fallback is not necessary.

Result on 2026-11-16: **G3 passes** on the synthetic corpus, the graph eval
and LongMemEval. Part (a) on real queries runs on the droplet in a later
task, after dk approves droplet access.

## Pass conditions

The conditions come from the plan (proposals that dk approved).

| Part | Condition |
|---|---|
| a. Same corpus, 500 or more queries | Vector search: same top 10 for 99% of queries. Hybrid search: same first result for 90% of queries, and a mean top-5 overlap of 0.90. |
| b. LongMemEval recall at 5 (no judge), and the graph eval | Not lower than Python by more than 1 point. |

a fixed seed: 300 keyword queries ("what about w1 w2?") and 300 starts of
records. `k` = 10, source prefix `g3/` (the corpus only).

| Metric | Result | Condition |
|---|---|---|
| Vector search: same top 10 (as sets) | 1.000 | 0.99 |
| Vector search: same top 10 in the same order | 1.000 | None |
| Hybrid search: same first result, keyword queries (300) | 0.953 | 0.90 |
| Hybrid search: same first result, record starts (300) | 0.957 | 0.90 |
| Hybrid search: same first result, all | 0.955 | None |
| Hybrid search: same first result, all, tie-aware | 0.957 | None |
| Hybrid search: mean top-5 overlap, keyword queries | 0.937 | 0.90 |
| Hybrid search: mean top-5 overlap, record starts | 0.965 | 0.90 |
| Hybrid search: mean top-5 overlap, all | 0.951 | None |
| Hybrid search: mean top-10 overlap, all | 0.954 | None |

The script applies the hybrid conditions to each query kind. A record start
is an easy query: its record is often first on the two servers. The keyword
queries alone must also pass.

Raw numbers: `G3-corpus-graph-2026-11-16.json` (debug build; the release
build gives the same numbers).

The hybrid differences come from the keyword scores. The Qdrant IDF formula
is `ln(1 + (N - n + 0.5) / (n + 0.5))`, and rank_bm25 uses
`ln((N - n + 0.5) / (n + 0.5))` with a floor (decision P0-2, difference 1).
The ranks of the keyword list are near the same, but not equal, so the fusion
can put a different record first. This test did not split the differences by
cause for each query.

## How the test works

`server/scripts/gate_g3.sh` runs the full test:

1. The Python server (`parity/run_python_server.sh`,
   `MEMORIES_PERSIST_DELAY_SEC=0`) gets the data through the HTTP API
   (`python -m parity.g3 seed`).
2. `memories-server migrate` copies a copy of the Python `metadata.json` into
   the collection `memories_v2`. The Rust embedder makes the dense vectors.
3. The two servers run at the same time. `python -m parity.g3 compare` sends
   each query to the two servers and applies the conditions. The script stops
   with exit code 1 if a condition fails, or if a part did not run (the result
   is then "partial"). `G3_ALLOW_PARTIAL=1` accepts a partial result.

The script stops if Qdrant has the collection `memories` or `memories_v2`. It
deletes the two collections at the end.

The Python server uses the same Qdrant server as the Rust server (collection
`memories`), as in production. The local (embedded) mode of `qdrant-client`
gives tied hits in a different order.

CI job `rust-parity` runs the corpus and graph parts on each push (about
3 minutes):

```bash
G3_PARTS=corpus,graph G3_ALLOW_PARTIAL=1 QDRANT_URL=http://127.0.0.1:6333 \
  server/scripts/gate_g3.sh server/target/debug/memories-server
```

The LongMemEval part is too slow for CI (about 1 hour on 4 CPUs, most of it
embeddings on the two servers). The full gate runs all three parts:

```bash
QDRANT_URL=http://127.0.0.1:6333 \
  server/scripts/gate_g3.sh server/target/release/memories-server g3.json
```

`G3_LME_EVERY` selects each Nth question (default 5, so 100 questions, the
same subset as the hybrid part of P0-2). All the questions are in one store,
each in its own source prefix. So the IDF counts all the questions, on the two
servers the same.

`tests/test_g3.py` checks the metrics and the gate conditions.

## Findings

1. **Duplicate texts.** The first corpus had 62 records with the same text as
   another record. Equal texts have equal scores, and Qdrant can put either
   one in the last place of the top 10. That gave a vector top-10 match of
   0.980, and all the differences were swaps of tied records (the tie-aware
   value was 0.998). The corpus now has unique texts, because a tie at the
   cut measures the Qdrant tie order, not the server. Production can have
   records with the same text. For such records, the Rust server and the
   Python server can return different tied records at the cut.
2. **The avgdl rule on a store that grows.** `python -m
   parity.keyword_index.run --dataset grow` adds 20,000 records: 2,000 short
   synthetic records first, then LongMemEval chunks. The average length grows
   from 14 to 310 tokens. At each 2,000 records, 200 queries compare three
   vectors with rank_bm25 (tie-aware overlap at 10):

   | Records | avgdl | Stale (avgdl at write time) | 25% rule | Exact |
   |---|---|---|---|---|
   | 2,000 | 14.8 | 0.998 | 1.000 | 1.000 |
   | 4,000 | 179.4 | 0.736 | 0.975 | 0.974 |
   | 6,000 | 232.3 | 0.778 | 0.974 | 0.975 |
   | 8,000 | 259.4 | 0.774 | 0.962 | 0.969 |
   | 10,000 | 276.3 | 0.765 | 0.964 | 0.964 |
   | 12,000 | 286.6 | 0.774 | 0.962 | 0.961 |
   | 14,000 | 295.7 | 0.775 | 0.954 | 0.959 |
   | 16,000 | 302.1 | 0.772 | 0.951 | 0.953 |
   | 18,000 | 306.8 | 0.770 | 0.950 | 0.955 |
   | 20,000 | 310.5 | 0.768 | 0.948 | 0.953 |

   At these checkpoints, the 25% rule stays within 0.008 of the exact
   average. Vectors that keep the average of their write time are much worse
   (0.77). The rule made 10 full passes. The checkpoints do not show the
   worst point of the rule, which is just before a pass, with the most drift.
   The test also measures that point: the overlap just before each of the 9
   later passes is 0.941 to 0.966 (the drift at a pass is 25% to 120%, because
   the test checks the rule after each 100 records). Raw numbers:
   `parity/keyword_index/results-grow-2026-11-16.json`.

   **Open work: the Rust server has no full pass yet.** The write path of
   task P3-1 gives each new or changed text a keyword vector with the current
   average (`writes.rs`), but no job writes all the vectors again. So the
   Rust server now behaves as the "stale" column: on a store where the average
   changes much after the migration, keyword search drops to about 0.77
   overlap. `migrate` writes all vectors with the exact average, so G3 is not
   affected. Task P3-4 (keyword vector refresh) owns the full pass.

   The test does not simulate the limit of 1 hour between passes. A bulk
   import that changes the average much (for example, long chunks into a
   store of short records) gives "stale" quality until the next pass, so for
   up to 1 hour. Task P3-4 adds this rule: start a pass with no time
   limit when the average is more than 2 times or less than half of the value
   of the last pass.

3. **Keyword scores in explain.** The `score` values of `bm25_candidates` in
   `/search/explain` are Qdrant scores. They are not equal to the Python
   values (the IDF formula). The parity cases of P2-2 mask them.
4. **The HNSW index is approximate on each server.** A first full run sent
   the corpus queries with no source scope, to a store of about 25,000
   records (the corpus plus the LongMemEval chunks). Qdrant then searches
   through its HNSW index, which can miss a near result. The vector top-10
   match fell to 0.907, and the hybrid first result of keyword queries to
   0.870. Each server missed results that the other one found with a
   higher similarity than its own tenth result. For example, for "what about
   check size health?" the Python list lacks record 71 (0.414284), which is
   above its tenth result (0.413745). An exact search cannot miss such a
   record, so the two indexes are approximate, each in its own way. The two
   collections have the default HNSW settings and the default search
   settings on the two servers. Raw numbers:
   `G3-unscoped-25k-2026-11-16.json`.

   Now the corpus queries use the source prefix `g3/`. With a filter of
   about 2,000 points, Qdrant searches the filtered points exactly, so the
   result does not depend on the size of the store.

   **Effect on part (a) with real data.** Production has about 66,000
   records, so its searches also go through HNSW. The condition "same top 10
   for 99% of queries" can then fail when two correct servers each miss
   different near results. Two Python servers on two HNSW builds would also
   differ. The droplet run needs a condition that allows for this, for
   example the recall at 10 of each server against an exact search, with
   Rust not lower than Python by more than 1 point. dk sets the condition.

5. **`eval/memories_client.py` batch size.** `MAX_BATCH_MEMORIES` is 1,000,
   but `/memory/add-batch` of v5.19.0 accepts at most 500 records. The G3
   harness sets 500. The eval client is not changed in this task.
