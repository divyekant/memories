# Gate G5: load (task P6-3)

Gate G5 measures the speed, the memory and the crash safety of the Rust
server under load. The test ran on two data sets:

- A synthetic corpus of 1,000,000 records.
- A read-only copy of the production data (92,287 records), approved by dk
  on 2026-11-16. The copy ran in a cloud session, not on the droplet. Nothing
  was written on the droplet. The local copy was deleted after the run.

Decision on 2026-11-17: **dk accepted G5.** The mixed add p95 stays open for
a later check. At the production rate (less than 0.1 request each second), an
add and a search seldom run at the same time.

Result on 2026-11-16: **G5 does not pass as written on the production data.**
The first run (embedder batch 64) failed two conditions: the add p95 in the
mixed scenario, and the memory limit. The second run (batch 16, the allocator
settings of production) passes the memory limit for the server process. The
add p95 in the mixed scenario still fails. The synthetic corpus passes each
condition except the memory peaks. On the same production copy, the Python
server v5.19.0 is much slower and uses three times the memory (see "Python
on the same data").

A container run with the limits of production found one more problem: a
migration inside `serve` left about 900 MB in the process. This PR moves that
migration to a child process (see "Container with the production limits").

## Machine and settings

- Cloud session, 4 vCPU, 15 GB RAM. Qdrant 1.15.4 in Docker on the same
  machine. The droplet has 4 vCPU too.
- Release build of `memories-server` from `rust-rewrite` at `159ad25`.
- ONNX Runtime 1.31.0, embedder batch size 64 (decision of P1-2; now 16,
  see finding 1).
- The LLM is a stub of the Ollama API (`parity/g5.py fake-llm`): 0.1 s for
  each call, 2 facts for each job, and ADD for each fact. 2 extract workers
  (the default).
- `benchmarks/load_test.py` with 5 workers. Each worker sends requests with
  a pause of 10 to 50 ms (no pause in burst). Search, add, burst and extract
  run for 60 s each. Mixed (70% search, 20% add, 10% delete) runs for 30 min.

CAUTION: The test load is about 20 to 120 requests each second, with no
stop. Production has about 2,350 searches and 417 extracts each day (P0-3
baseline), that is less than 0.1 request each second on average.

### Memory

RSS of the process, sampled each 0.2 s (`rss-*.json`, MB).

| Step | Synthetic, 1,000,000 records | Production copy |
|---|---|---|
| `migrate` (copy of the vectors) | 3,371 peak | 677 peak |
| `migrate` with embedding (10,000 synthetic records, no old collection) | 856 peak (VmHWM 877) | not run |
| `serve`, start | 646 peak, then 330 (fixed, see below) | 330 |
| `serve`, search, add, burst, extract | 328 to 348 | 321 to 345 |
| `serve`, `/memory/add-batch` (5 batches of 64 long texts) | 885 peak (VmHWM 981) | 898 peak (VmHWM 994) |
| `serve`, 30 min mixed, after add-batch | 390 to 391 | 412 to 425 |
| `verify --sample 1000` | 2,849 peak | 678 peak |

Findings:

1. **Bulk peak of the embedder.** A batch of 64 long texts takes the RSS to
   830 to 960 MB, as decision `2026-11-16-rust-embedder.md` predicted. After
   the batch, the RSS stays about 70 MB higher (345 to 414 MB on the
   production copy). This is why the steady memory of the production copy is
   above 400 MB. The embedder example measured these values (1,000 fixture
   texts, two rounds, 4 vCPU):

   | Batch size | Peak (VmHWM) | RSS after | Time for 1,000 texts |
   |---|---|---|---|
   | 64 (now) | 832 MB | 225 MB | 28 to 30 s |
   | 32 | 549 MB | 247 MB | 23 to 26 s |
   | 16 | 394 MB | 209 MB | 21 to 22 s |

   A batch of 16 is under the limit and faster. The vectors do not change,
   because the padding of a batch does not change a vector (gate G2). dk
   chose batch 16 on 2026-11-16, and this PR sets it. The load runs above
   used batch 64. The second run on the production copy used batch 16 (see
   "Second run on the production copy").
2. **Start peak at 1,000,000 records (fixed).** At each start, the server
   read all of `metadata.json` into memory to hash it. At 1,000,000 records
   (634 MB), the start peak was 646 MB. `file_sha256` now reads the file in
   blocks of 1 MiB. The run did not measure the start again after the fix.
3. **`migrate` and `verify` hold all of `metadata.json`.** They use about
   3.4 times the file size (3.4 GB for 634 MB). They run once, before the
   server starts. On production (75 MB), the peak is 677 MB. A streamed read
   is the fix if an install has a much larger file.
4. **Steady memory grows slowly with the record count.** 330 MB at 92,287
   records and at 1,000,000 records before a bulk batch. The record catalog
   is not the main cost.

## Forced stop and verify

1. The server started again, a mixed load ran, and 200 extract jobs went
   into the queue. Then `kill -9` stopped the server. The queue held 196 jobs
   (synthetic) and 2,028 jobs (production) at the stop.
2. After the restart, each of the 200 jobs completed. No job was lost or
   stuck. The start after the stop took 27 s (synthetic) and 6 s
   (production).
3. `memories-server verify --sample 1000` after the stop:

   | Check | Synthetic | Production copy |
   |---|---|---|
   | Records of the corpus missing | 0 | 0 |
   | Vector differences (1,000 samples) | 0 | 0 |
   | Records added by the load (`extra`) | 16,152 | 10,982 |
   | Field differences | 225, only `last_reinforced_at` | 562, only `last_reinforced_at` |

   `verify` reports `ok: false` after a load by design: it compares with
   `metadata.json`, and the load adds records and reinforces search hits (as
   the Python server does). In these two runs, the gate script read only the
   20 records that `verify` lists, and those had only a change of
   `last_reinforced_at`. The script now reads each record of the collection,
   fails on any other changed field, on a count gap or on a `verify` error,
   and fails if no job waited in the queue at the stop. Directly after the
   migration, `verify` passed with no difference on the two data sets.

## Allocator settings

Search scenario, 60 s, 5 workers, two runs of each setting, on the
production copy.

| Settings | Search p95, run 1 / run 2 (ms) | VmHWM |
|---|---|---|
| Default glibc | 470 / 328 | 350 MB |
| `MALLOC_ARENA_MAX=2` only | 589 / 613 | 299 MB |
| The three settings of production | 672 / 705 | 289 MB |

The settings save about 60 MB and make the search p95 about 40% to 100%
slower. `MALLOC_MMAP_THRESHOLD_` and `MALLOC_TRIM_THRESHOLD_` cost the most.
These settings were for the Python server. Do not set
`MALLOC_MMAP_THRESHOLD_` and `MALLOC_TRIM_THRESHOLD_` for the Rust server.

## Container with the production limits

The Rust binary (batch 16) ran in `ubuntu:24.04` with `--memory 4g
--memory-swap 8g --cpu-shares 2048`, as the droplet runs the Python server.
`serve` did the first-start migration itself, as on the droplet. Search 60 s,
add-batch (5 batches of 64 long texts), extract 20 s, then mixed 10 min.

| Measure | Default glibc | Production allocator settings | Default glibc, migration in a child process |
|---|---|---|---|
| Search p95 | 422 | 689 | 409 |
| Mixed, search p95 | 337 | 605 | 359 |
| Mixed, add p95 | 461 | 680 | 462 |
| Mixed, requests in 10 min | 12,857 | 9,149 | 12,331 |
| RSS of `serve` after the migration | 1,193 to 1,203 MB | 903 MB | 383 to 388 MB (peak 525 MB in add-batch) |
| `docker stats` at the end | 1.155 GiB | 882 MiB | 367 MiB |

Finding 5: **the first-start migration held about 900 MB in `serve`.** The
migration reads all of `metadata.json` (finding 3). After the migration, the
allocator keeps that memory in the process until the stop. The gate script
runs `migrate` as a separate process, so the first runs did not show the
problem. The fix: `serve` now starts `memories-server migrate --sample 1000`
as a child process with the same environment. When the child stops, its
memory goes back to the system. If the child fails, `serve` stops, as before.
With the fix, the RSS of `serve` stays under 400 MB in the container, and the
latency does not change. The memory peak of the container was 823 MiB, during
the child migration.

## How the test works

`server/scripts/gate_g5.sh` runs the full test:

```bash
QDRANT_URL=http://127.0.0.1:6333 \
  server/scripts/gate_g5.sh server/target/release/memories-server <out dir>
```

- `parity/g5.py corpus` writes the synthetic `metadata.json` and the old
  Python collection. The texts have 10 to 80 words from a vocabulary of
  6,000 made-up words (Zipf frequencies). 5% of the texts have 300 to 500
  words. Each vector is a real embedding of a pool text with a small change.
- CAUTION: Point `QDRANT_URL` only at a test Qdrant server. With
  `G5_DATA`, the cleanup deletes `G5_COLLECTION`, so a production server
  would lose its collection.
- For the production copy, set `G5_DATA=<dir>` and
  `G5_COLLECTION=<old collection>`, with `G5_EMBED_COUNT=0`. `config.json`
  must name that collection.
- `G5_COUNT`, `G5_SHORT` and `G5_MIXED` change the size and the times. The
  full synthetic run takes about 55 min. The production run takes about
  41 min.
- `tests/test_g5.py` tests the corpus, the LLM stub and the RSS sampler.

Raw numbers of the two runs: `G5-2026-11-16.json`.

The production copy came from the droplet with read-only commands: `sudo cat`
of `metadata.json` and `config.json`, and a Qdrant scroll through an SSH
tunnel. The Qdrant copy had 8 more points than `metadata.json` (the persist
delay of the Python server).
