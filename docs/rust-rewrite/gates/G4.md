## Part a: method

Part a has two checks. The two checks run in CI for the Python server and for
the Rust server (`.github/workflows/ci.yml`, jobs `parity` and `rust-parity`).

| Check | Driver | Golden file | Cases |
|---|---|---|---|
| Pipeline cases (task P4-3) | `parity/extract_pipeline.py` | `parity/golden/extract/pipeline.ndjson` | 16 cases with scripted replies |
| Eval corpus (task P4-4) | `parity/extract_corpus.py` | `parity/golden/extract/corpus.ndjson` | 105 transcripts and the final records |

To run the eval corpus check, from the repository root:

```bash
server/scripts/parity_pipeline.sh python --check extract_corpus
server/scripts/parity_pipeline.sh server/target/debug/memories-server --check extract_corpus
```

The Rust run needs `QDRANT_URL` and `ORT_DYLIB_PATH`. To write the golden file
again from the Python server, use `--record` in place of `--check`.

The transcripts are the texts of the two extraction evals:

- The 20 texts of `CORPUS` in `eval/run_extraction_eval.py`. The contexts
  rotate: `stop`, `pre_compact`, `session_end`. All use the source `eval/g4`.
- The 85 scenario memories that `eval/run_scenario_extraction_eval.py` sends to
  `/memory/extract`, in the same order. Three quarters use the source
  `eval/g4`. One quarter keeps the scenario source, so that some decisions
  point to a record of another source and give an `error` action.

The store starts empty and grows, so later transcripts find similar records.
A fake OpenAI chat server gives the LLM replies. Each reply is a function of
the prompt and of the highest record ID that earlier jobs returned:

- Fact extraction: up to 4 sentences of the transcript, with mixed category
  case and three reply formats (plain JSON, a code fence, text before the
  array).
- Decision: for each fact, an action from a hash of the fact text. The target
  is the lowest ID of the similar records with the highest shown relevance.

The 105 jobs gave these actions on the Python server: 72 add, 36 noop, 18
delete, 16 update, 16 conflict, 2 skipped and 47 error. 86 records are stored
at the end.

## Part a: pass condition

The proposal of the plan was: the prompts are equal byte for byte, and the
decisions and stored records are equal for 100% of cases.

The similar records in the decision prompt come from hybrid search. The Rust
keyword index is a Qdrant sparse vector. Its scores are close to the rank_bm25
scores of Python, but not equal (`docs/decisions/2026-11-16-rust-keyword-index.md`).
Thus, on a store that grows, a similar list can differ when two records have
almost the same score. The check uses this condition:

| Item | Condition |
|---|---|
| Fact extraction prompts | Equal byte for byte |
| Decision prompts outside the similar lists | Equal byte for byte |
| JSON format of the similar lists | The Python format (compact JSON, ASCII escapes) |
| Text of a record that is in the similar lists of the two servers | Equal |
| Actions, counts, errors and links of each job | Equal |
| Compaction candidates without their IDs and scores (`fact_index`, `sources`, `cross_source`) | Equal |
| Stored records at the end (text, source, flags, supersede and conflict fields, links) | Equal |
| IDs and order of the similar lists, IDs of the compaction candidates | The gate G3 tolerance for hybrid search: 90% or more of the similar lists are equal, and the mean overlap of the IDs is 0.90 or more |
| Shown relevance, RRF scores | Not compared |
| Input tokens of the decision call | Equal, except in a case whose similar lists differ |

dk must approve this change of the pass condition.

## Known difference that the driver avoids

Python gives the ID of a deleted record again when that record had the highest
ID. The engine calls `_rebuild_id_map` after each add, and that sets the next
ID to the highest stored ID plus 1. Thus the reuse occurs at the next add in
the same process, not only after a restart. The Rust counter never gives an ID
again (`docs/decisions/2026-11-16-rust-record-store.md`). The fake LLM never
deletes the record with the highest ID, so that the IDs of the two servers
stay equal.
